Inside motion-screen

Twelve modules in two halves that are never allowed to meet, plus one file where they do — on purpose, so the leak has somewhere to be audited.

The organising idea

Two paths that must not touch

The whole repo is shaped by one constraint. The screener decides from a camera estimate of the scene; the oracle decides from the true scene. If any information leaks from the second into the first, every number the project produces is worthless and nothing about the code would look wrong.

So the two paths are separate all the way down, and they are brought together in exactly one file. That file is where you audit.

Known gaps

Two things the architecture doesn't yet do

The feasibility gate is not in the pipeline. The control that removes 34% of all unsafe candidates — and the only one that improves safety and yield together — exists as an analysis that was run, not as a function anything calls. Every other number in the repo describes code that executes.
The sphere proxy has holes. Every fitted link fails hull-interior coverage, with gaps up to 59.8 mm. Covering a link's vertices does not cover its convex hull when the cover is a union of spheres, and MuJoCo collides meshes as their hull. So this screener's clearance verdicts are excellent heuristics — 384 out of 384 correct — rather than proofs. That is precisely what the kccd-screener rebuild fixes.
Twelve modules, ~3,100 lines. The companion repo kccd-screener answers the narrowed brief: arm-vs-arm only, no camera, no simulator at runtime, sound by construction.
